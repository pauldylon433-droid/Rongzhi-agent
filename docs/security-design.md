# 安全设计说明

本文件说明「融智 Agent」在安全与防篡改方面的设计约定。当前为竞赛演示项目，全部为模拟数据，
运行在模拟银行环境中，不接入真实资金与真实账户。

## 一、身份与数据归属

- **单用户演示模式**：服务端固定演示用户「张三」（`resolveDemoUser`），不接受客户端通过
  `user_id` 切换用户；所有查询与转账均按该用户限制数据范围。
- **尚未实现正式登录认证**：这是当前明确限制，接口不提供身份凭证校验，仅供演示。
- 转账单的归属校验：`ref_no` 对应的 `user_id` 必须等于服务端演示用户，否则视为不存在（404 / not_found）。

## 二、金额安全

- 金额统一使用**整数分**存储与计算，字段以 `_cents` 结尾。
- 输入必须为**正整数安全整数**（`Number.isSafeInteger`），拒绝小数分、负数、NaN、超大数与非法类型。
- 前端元 → 分转换使用**字符串拆分**（`yuanToCents`），不依赖浮点乘 100，避免精度误差。

## 三、转账风险与状态机

- 风险级别由**后端判定**，前端或模型无法指定：`日累计成功转账金额 + 本次金额 ≤ 100000 分（¥1000）`
  为黄色（待确认）；超过为红色（需要交易密码 + 手机验证器动态码强验证）。这不是单笔金额判断。
- 日累计按 **Asia/Shanghai 自然日**（左闭右开）统计 `status='completed'` 且 `confirmed_at` 落在当日范围内的转账。
- 状态机：`pending`（待确认）、`needs_verification`（需强验证）、`completed`（已完成）、
  `cancelled`（已取消）、`expired`（已过期）、`failed`（失败）。除到期外不允许任意跳转：
  - `pending → completed`：仅确认接口，且需通过余额 / 账户 / 累计校验；
  - `pending → cancelled`：仅取消接口；
  - `pending → expired`：超过有效期（5 分钟）后惰性标记；
  - `pending → needs_verification`：确认时累计过线；
  - `pending → failed`：确认时账户异常或余额不足；
  - `needs_verification → completed`：仅强验证接口（交易密码 + 动态验证码均正确且通过校验）；
  - `needs_verification → cancelled`：可取消；`needs_verification → expired`：超过有效期；
  - `needs_verification` 不可通过普通确认绕过，`completed` 不可取消或重复执行。

### 银行卡冻结 / 解冻状态机（后端判定）

银行卡操作同样由后端判定风险与合法性：冻结为黄色（待确认）、解冻为红色（需强验证）。

- 合法状态流转：`active → frozen`（冻结）、`frozen → active`（解冻）；已注销（cancelled）卡不可冻结 / 解冻，
  已处于目标状态的卡拒绝重复创建操作单，未知状态一律拒绝。
- 创建操作单（prepare）**不改变卡片状态**，写入建单时卡片版本快照 `card_version`。
- 卡片状态更新用**乐观锁版本 CAS**：`UPDATE cards SET status=?, version=version+1 WHERE id=? AND status=? AND version=?`。
  建单后卡片被改动（含「正常→冻结→正常」回环）的旧单不可覆盖新状态（返回 `stale` / 标记 `failed`）。
- 状态机：`pending`（冻结待确认）/ `needs_verification`（解冻待强验证）→ `completed` / `cancelled` / `expired` / `failed`，
  除到期外不允许任意跳转；解冻单不可通过普通确认接口执行；`completed` 不可取消或重复执行。
- 冻结 / 解冻**仅改变卡片状态**，不改变余额、交易流水、订阅与日限额；不涉及真实扣款或真实卡片操作。

### 订阅 / 代扣状态机（后端判定）

订阅操作同样由后端判定风险与合法性：暂停为黄色（待确认）、取消为黄色（待确认）、恢复为红色（需强验证）。

- 合法状态流转：`active → paused`（暂停）、`paused → active`（恢复）、`active → cancelled` / `paused → cancelled`（取消）；
  已取消（cancelled）为终态，不可暂停 / 恢复 / 取消；已处于目标状态的订阅拒绝重复创建操作单，未知状态一律拒绝。
- 创建操作单（prepare）**不改变订阅状态**，写入建单时订阅版本快照 `subscription_version`。
- 订阅状态更新用**乐观锁版本 CAS**：`UPDATE subscriptions SET status=?, version=version+1 WHERE id=? AND version=?`。
  建单后订阅被改动（含「生效→暂停→生效」回环）的旧单不可覆盖新状态（返回 `stale` / 标记 `failed`）。
- 状态机：`pending`（暂停 / 取消待确认）/ `needs_verification`（恢复待强验证）→ `completed` / `cancelled` / `expired` / `failed`，
  除到期外不允许任意跳转；恢复单不可通过普通确认接口执行；`completed` 不可取消或重复执行。
- 暂停 / 取消 / 恢复**仅改变订阅状态**，不改变余额、交易流水、银行卡状态、金额、周期或原扣费日期；不取消真实商户合约，
  也不触发真实扣款。暂停 / 取消后不再提示「即将扣费」；恢复后若原扣费日期已过，仅显示「扣费日期待更新」，不编造日期。

## 四、强验证（交易密码 + 动态验证码，转账、解冻与订阅恢复共用）

红色转账单、解冻单与订阅恢复单（均为 `needs_verification`）必须同时通过**交易密码**与**手机验证器动态验证码（TOTP）**验证，
再由用户明确点击「验证并确认」，不能通过普通确认接口绕过。

- **凭据保护**：交易密码用随机盐 + scrypt 哈希（`timingSafeEqual` 比对）存储；TOTP 密钥用
  AES-256-GCM 认证加密后存储，加密主密钥与数据库分离保存（`backend/data/.verification-key`，
  受限文件，禁止硬编码 / 提交 Git）。未绑定 / 缺密钥 / 解密失败时红色单保持阻断。
- **TOTP**：RFC 6238（HMAC-SHA1、6 位、30 秒、±1 时间步窗口），验证器名「融智 Agent」，账户标签为演示账户。
  本地生成二维码，不调用第三方二维码服务。
- **防重放**：成功消费的 TOTP 时间步写入 `totp_used_steps`（`UNIQUE(user_id, step)`），跨单 / 并发 /
  重启不可复用；绑定验证码同样被消费，不可二次使用。已验证通过 / 已取消 / 已过期的单不可再通过验证执行。
- **失败锁定**：连续 5 次密码或验证码错误锁定 15 分钟（跨单 / 重启不失效，到期自动解锁）；失败计数与
  审计独立提交，不被业务事务回滚吞掉；与请求级限流分离。
- **事务一致**：验证请求绑定到具体 `ref_no`，服务端重新读取并校验归属 / 状态 / 有效期 / 账户 / 余额 /
  当日累计；凭据正确后在同一事务内「消费时间步 + 扣款 + 入账流水 + 状态更新 + 审计」。
- **审计最小化**：只记录绑定成功 / 验证失败 / 锁定 / 验证成功 / 执行结果，**绝不**记录密码、验证码、
  TOTP 密钥或完整敏感请求体。
- **本地绑定**：不提供任意 Web 绑定 / 重置 / 替换接口；由用户本人执行一次性本地交互命令
  `node backend/scripts/bind-verification.js`（隐藏输入 + 双重确认交易密码、随机 TOTP 密钥、
  临时二维码、输入验证码通过后才启用绑定，完成后清理临时明文）。已有绑定拒绝覆盖，无快捷重置。
- **AI 边界不变**：AI 仍不开放任何「执行转账 / 执行冻结解冻 / 执行订阅操作 / 校验密码 / 校验验证码」的模型工具；强验证凭据仅发往专用验证接口。
- **跨业务共用（转账、解冻与订阅恢复）**：解冻与订阅恢复复用同一套凭据保护 / TOTP / 防重放 / 失败锁定；三者共享同一用户的
  `totp_used_steps` 与 `verification_failures`，已用于转账的时间步不可再用于解冻或订阅恢复（反之亦然），
  跨业务累计失败同样锁定 15 分钟，不另起第二套独立规则。

## 五、防重复执行

转账确认在**同一个数据库事务**内完成：扣款 → 写入已入账转账流水 → 更新状态为已完成 → 写审计，
并叠加两层防线：

1. **状态 CAS**：`UPDATE ... SET status='completed' WHERE id=? AND status='pending'`，仅 pending 能认领；
2. **唯一关联索引**：`transactions.transfer_ref` 建立 UNIQUE 索引，同一转账单最多对应一条流水。

重复点击、重发请求、并发确认只会执行一次；重复查询 / 确认已完成操作返回原回执。余额不会出现负数
（扣款使用 `balance_cents >= ?` 守卫，失败则整个事务回滚）。

## 六、确认请求不可篡改

- 确认 / 取消请求只接受 `{ confirm: true }` / `{ cancel: true }`，额外字段返回 400。
- 确认时从数据库读取原操作快照（付款账户、收款人、金额、备注），**不接受请求重新指定**金额或收款人。
- 创建请求白名单字段（`recipient_id` / `amount_cents` / `remark`），多余字段返回 400。

## 七、AI 助手安全边界

- AI 助手工具白名单共 **20 个**（与源码 `TOOL_DEFS` 一致）：
  - 账户 / 分析：`get_accounts`、`get_monthly_analytics`、`get_transactions`
  - 转账：`search_transfer_recipients`、`list_transfer_recipients`、`prepare_transfer`、`get_transfer_status`
  - 银行卡：`get_cards`、`prepare_card_operation`、`get_card_operation_status`
  - 订阅 / 跨场景：`get_subscriptions`、`prepare_subscription_operation`、`get_subscription_operation_status`、
    `start_subscription_review`
  - 信用卡：`get_credit_accounts`、`get_statement`、`prepare_repayment`、`get_repayment_status`
  - 安全 / 计划：`analyze_transactions_sandboxed`、`plan_workflow`
  其中 `prepare_transfer` / `prepare_card_operation` / `prepare_subscription_operation` / `prepare_repayment`
  只能生成「待确认单」，**绝不扣款、绝不改卡片 / 订阅 / 扣款来源**；执行必须由用户在界面
  点击确认或强验证后，调用现有确认 / 验证接口完成。
- **不开放任何扣款 / 执行 / 强验证工具**（如 `confirm_transfer`、`confirm_card_operation`、`verify_card_operation`、
  `confirm_subscription_operation`、`verify_subscription_operation`）；模型请求确认、改余额、改卡片 / 订阅状态、写库等
  一律被拒。「确认」「我同意」「跳过验证」等聊天文字不会触发扣款、冻结 / 解冻或订阅暂停 / 恢复 / 取消。
- 转账 / 银行卡 / 订阅工具均不接受模型传入用户身份、风险等级、确认状态或验证状态；收款人、付款账户、目标卡片、目标订阅
  均由服务端校验归属与状态；**不存在**任何客户端「verified」布尔标记，凭据只能经专用验证接口提交。
- 金额参数 `amount_yuan` 为字符串，服务端用字符串拆分精确转换为整数分（拒绝负数、零、超过两位小数、
  科学计数法、超出安全范围；不采用浮点乘 100）。
- 单条用户消息最多生成一张转账单 / 一张银行卡操作单 / 一张订阅操作单；会话维护「当前待确认单」引用，用户修改请求时
  服务端取消旧单，旧确认卡因此不可再执行。模型重复工具调用不能生成重复操作单（同消息内去重）。
- 改单 / 改操作单的旧 / 新单状态与文案**由后端确定性生成**（`prepare_transfer` / `prepare_card_operation` 返回
  `previous` 与 `notice`），不依赖模型推断、不靠加强提示词保证正确；模型文字不作为操作成功依据。新单创建失败时如实
  说明「原单未变更」；旧单已完成时 `previous.status='completed'` 且不会被取消。前端旧卡依据信号自动回读数据库状态，
  但**后端仍以状态 / 版本 CAS 拒绝确认已取消的旧单**，不单靠前端禁用按钮。
- 银行卡多张时列出掩码卡号选项、不擅自选第一张；卡片模糊时先澄清。用户提到「挂失 / 销卡 / 补卡 / 调额」时明确
  说明不支持并询问是否改用「临时冻结」，不替用户决定。
- 订阅操作同样：多个订阅匹配或指向不明确时先澄清，不擅自选第一项；已取消订阅不可再操作，恢复需强验证，
  暂停 / 取消为普通确认。用户仅回复「确认」等文字不触发订阅状态变更，须在确认卡上明确操作。
- 模型不能通过工具写库、传 `user_id`、SQL、文件路径、URL；未知工具 / 额外参数 / 非法参数均被拒。
- `analyze_transactions_sandboxed` 只在专用 Worker 中的 QuickJS WebAssembly 沙箱处理脱敏流水；无网络 / 文件系统 / 宿主绑定，
  输出经 schema 与独立复算校验并标记为非权威；`plan_workflow` 只创建受约束 DAG 计划，不确认 / 扣款 / 验证。

### 聊天历史保留与模型上下文

- **不按闲置时长删除**：会话与消息不会因 7 天（或其它闲置时长）未活跃而被清理；
  `GET /api/assistant/current`、历史列表、新建会话、打开旧会话都不删除历史。
- **模型上下文有上限**：仅保留最近 **8 轮**（按轮裁剪，工具调用与结果配对完整保留）；
  单会话可见消息最多 **200 条**，超出时删除最旧的可见消息；不承诺超出此上限的历史仍可查看。
- **不提供无限记忆**：不以扩大模型上下文的方式换取“记住更多”，也不承诺无限上下文。

### 能力边界与已知限制（如实说明）

- **无代码执行沙箱**：模型不执行任何代码、SQL、URL 或文件操作；工具是服务端固定白名单函数，
  参数经类型 / 枚举 / 归属校验。这里的“AI 边界”是工具面与执行面的限制，不是通用代码沙箱。
- **受限模板 DAG**：跨场景仅「订阅审查」一条固定 7 节点模板，由服务端构建与校验；
  不是通用工作流引擎，也不执行模型生成的步骤。
- **事务回滚 ≠ 撤销已完成业务**：确认过程中的异常会使同一事务整体回滚（不产生半完成状态）；
  但已完成的操作（扣款 / 入账 / 冲抵）是业务事实，系统不提供“回滚已完成操作”的能力；
  取消只适用于尚未执行的 pending / needs_verification 单据，属于状态变更，不是撤销已发生的资金变动。
- **统计口径差异**：页面月度分析按当前所选账户过滤；AI 的 `get_monthly_analytics` 当前返回**全账户**合计，
  不接收账户参数。两者不能混用，本轮不新增工具能力。
- **模型配置**：源码默认模型为 `deepseek-flash`（与 `.env.example` 一致）；运行中可由环境变量覆盖。
  部署时曾以进程覆盖为 `deepseek-flash`（源码原默认 `deepseek-v4-pro`），本次已统一为 flash，避免误用高费用模型。
- **无系统级模型对抗保证**：提示约束、输入 JSON 序列化与“明确标注凭据”的入口拦截属于纵深防御，
  不等于完整 Prompt 注入防御；真实模型的对抗行为未经系统验证。

### 跨场景任务安全边界（订阅审查单链）

- **唯一任务链**：当前仅支持一条任务链「分析某月支出 → 列出生效订阅 → 用户选择 → 准备暂停单 → 界面确认 →
  核验 → 汇总回执」，任务类型 `subscription_review`；其它任务组合一律说明「不支持」，不提供通用工作流编排框架。
- **白名单任务图**：任务由服务端用白名单节点（7 个 `node_key`）构建并校验（key 唯一、依赖存在、无环、顺序连续），
  **不执行模型生成的任意代码 / URL / SQL / 操作步骤**；模型只负责理解意图与提取月份（`month` 经 `parseMonth` 严格校验），
  不能注入节点、依赖或业务步骤。
- **模型不代用户决策、聊天文字不执行**：模型不能代用户选择订阅；订阅选择只能经 `POST /api/agent-tasks/:taskNo/select`
  （服务端校验归属与生效状态）完成；生成暂停单后订阅状态不变，确认只能经订阅操作单确认接口点击执行，
  聊天文字「确认」不推进任务。
- **只读节点自动执行，变更复用操作单**：月度分析复用 `monthlyAnalytics`、订阅查询复用 `listSubscriptions`（均为只读）；
  「准备暂停单」复用 `createSubscriptionOperation`（只生成操作单，不执行），与订阅管理的版本 CAS / 风险判定 / 审计同一套规则。
- **节点完成以服务端事实为准**：任务推进由服务端对账驱动（核验操作单 `completed` + 业务库订阅确实 `paused`），
  不由模型回复或界面文案决定；查询结果带 `month` / `as_of` 快照标记，不冒充实时数据。
- **竞态与阻断**：暂停 / 取消 / 转手动在后端调用 `cancelSubscriptionOperation` 阻断关联未执行操作单（不仅隐藏前端按钮）；
  确认与取消竞态以事务结果为准，已确认的订阅变更不因任务取消 / 失败 / 转手动被反向。
- **恢复不重放**：刷新 / 后端重启经只读对账恢复任务，不重发模型请求、不自动重发业务操作；过期 / 失效单需重新生成并再次确认。
- **诚实不编造**：无使用频率数据则不声称「长期未使用」；不同扣费周期不直接相加成月度费用；暂停成功不等于已退款 / 已实现节省金额。

## 八、敏感信息与错误处理

- 不读取、不打印、不复制 `.env` 中的真实密钥内容。
- 错误响应不泄露密钥、原始异常、SQL 语句、堆栈与数据库文件路径。

## 九、一致性与备份

- 结构变更前使用 SQLite `backup()`（正确处理 WAL）创建一致性备份：`backend/scripts/backup-db.js`。
- 余额与已入账流水强一致：`余额 = 期初余额 + 已入账收入 − 已入账支出`（含转账流水）。

## 十、结构化审计

- `audit_events` 记录 `request_id` / `session_id` / `plan_id` / `tool_call_id` / `operation_ref` / category / action / result / risk / detail。
- 助手记录请求（消息长度 / SHA-256，不落原文）、每次工具调用（脱敏参数、结果、耗时、操作单号）、回复摘要（不含思维链）；API 中间件记录状态变更请求；DAG 记录计划动作。
- 密码 / 验证码 / TOTP 种子 / API Key / 加密密钥 / 哈希盐 / 沙箱代码原文不入审计；沙箱代码只记录长度与 SHA-256。
  除按键名脱敏外，自由文本中的常见密钥格式与「密码是 …」「API Key: …」「Bearer …」等显式模式也会清理；
  这不等于「识别所有任意未标注秘密」。
- 计划动作、工具、操作单、确认 / 验证与只读刷新触发的核验共享请求上下文与 `operation_ref`；
  异步请求追踪写入失败会重试两次并记录可核查的失败状态（本地 `audit_trace_failures` / 云端独立审计事件）。
- 审计查询按数据库条件过滤 / 分页（CloudBase 使用固定 `audit_query_v1` RPC），不依赖快照最近 2000 条。
- 业务成功审计仍在业务事务内（`audit_logs`）；安全失败 / 可疑行为事件独立提交，不随业务回滚丢失。
- `/api/audit/timeline` 与 `/api/audit/export` 默认不暴露（未配置 `AUDIT_ACCESS_TOKEN` 返回 404），配置后必须 Bearer / `X-Audit-Token`。

## 十一、异常熔断

- 请求限流：内存令牌桶，按 IP / 接口返回 429，不修改持久业务状态。
- 强验证锁定：`verification_failures` 行锁 + 5 次 / 15 分钟；晚到失败不清锁；业务提交在事务内复核锁定；跨实例以数据库行为准。
- 可疑行为锁定：`security-guard` 基于服务端拒绝 / 工具拒绝事件计数，按 IP / 会话 scope 隔离；阈值 / 窗口 / 锁定时间由 `SECURITY_ANOMALY_*` 配置；锁定事件写入审计；不按提示词关键词判定。
  计数 / 锁定 / 到期使用独立持久状态（本地 `security_scope_state`、云端 `rongzhi_bank_security_scope_state` + 固定 RPC），
  不从审计最近 N 条推导，跨 scope 事件洪泛不会提前解锁；状态存储故障时敏感写操作返回 503（只读查询仍可用）。
  代理来源必须显式配置 `TRUST_PROXY`（默认不信任 `X-Forwarded-For`）。
  CloudBase 网关部署使用 `TRUST_PROXY=cloudbase`：只取网关注入的 `X-Original-Forwarded-For` 最后一段
  （实测网关会把真实客户端 IP 追加到链尾，而 `X-Forwarded-For` / `X-Real-IP` 会透传客户端伪造值）；
  该模式下不启用 Express 的 `X-Forwarded-For` 信任，直接暴露服务时仍回退 socket 地址。
- 模型服务熔断：本地与云端共用 `createModelBreaker`；连续真正模型故障达到 `MODEL_BREAKER_THRESHOLD` 后在
  `MODEL_BREAKER_COOLDOWN_MS` 内快速失败，返回 503 `model_breaker`；配额 / 并发 / 请求限流拒绝发生在熔断之外，不计入提供方故障。
- 单个 scope 锁定不会锁死整个共享服务；其他 IP / 访客不受影响。

## 十二、代码沙箱

- `services/sandbox.js` 在专用 `worker_threads` 中启动独立 QuickJS WebAssembly 运行时执行模型生成的脱敏流水分析代码；
  主线程事件循环不被同步执行阻塞，父线程可独立超时并 `terminate` 执行单元。
- 输入只含金额 / 方向 / 分类 / 状态 / 时间 / 商户哈希 / 账户哈希，不含账户余额、账户名、用户或密钥。
- 无 Node `require` / `process` / `fetch` / `fs` 或任何宿主函数；无网络、无文件系统、无银行写接口。
- 限制：2 秒执行墙钟（父线程另设 250ms 宽限）、32 MB 堆、1 MB 栈、16 KB 输出、8000 字符代码；
  默认最多 2 个并发执行单元、20 个排队、排队超时 5 秒；超限中断并丢弃整个 runtime。
- 结果必须符合可展示分析 schema（`total_cents` / 可选 `count` / `by_category` 等）；主线程按脱敏输入独立复算合计、
  计数与分类，不一致或含额外指令字段 / 负数 / 非整数时标记 `analysis_unverified` 并拒绝。
- 结果带 `sandbox=quickjs-wasm`、`execution_unit=worker_thread`、排队 / 执行耗时、资源限制、退出状态与代码 SHA-256；
  仍标记 `authoritative:false`，不得作为余额 / 交易事实。
- 边界：这是 Worker + WASM 运行时隔离，不是 OS 容器；若赛题强制要求容器级隔离，需部署 Docker / Firecracker 等额外后端。

## 十三、受约束 DAG 计划

- 两条白名单链：`subscription_review`（月度分析→选择订阅→暂停/换来源→确认→核验）与 `repayment_review`（信用卡账单→选择范围/付款账户→建单→强验证→核验）。
- 模型只能提交 flow / 参数 / 可选步骤依赖；服务端校验节点白名单、依赖与模板完全一致（不能删除 / 增加 / 重复 / 逆置业务边）、
  无环、最多 12 步；参数按 flow / 阶段严格 schema 校验（非法枚举、额外字段、非法类型直接 400）。
- 计划持久化到 SQLite `workflow_plans` / CloudBase `rongzhi_bank_workflow_plans`；建单与计划版本校验在同一事务
  （本地 SQLite 事务 / 云端 plan RPC 行锁 + 版本 CAS），操作单编号确定性绑定计划与版本，失败不留孤单。
- 支持等待选择、暂停、继续、取消、重试、修改未执行步骤、转人工；修改会取消旧待确认操作单并使原确认失效。
- 只读节点失败会阻断选择；核验前必须先完成确认 / 强验证节点；计划完成要求所有节点 completed；
  恢复 / 修改时重新查询只读节点并记录查询时间，查询失败在视图中显式返回。
- 已完成操作只核验真实状态，不提供直接撤销；回退只重置未执行节点。
- 「计划任务」页面已接入新版计划入口（与旧「最近任务」分开），复用订阅 / 还款操作单确认卡。
